# Customer intelligence roadmap and checkpoints

## Phase 0 — Audit

Existing data: tenant-scoped Customer (phone, email, page identity, orders/spend), Conversation (channel, control mode, sales stage, metadata), Message (attachments, products, intent, human source), Product/inventory, Knowledge, Order (payment status and Steadfast courier state). Authentication establishes AsyncLocalStorage tenant context; model hooks scope queries and aggregation. Public website channels resolve a tenant separately. Messenger already validates signatures and queues idempotent events. Steadfast already provides credential management and shipment synchronization. Merchant billing is separate from customer payments.

Frontend: merchant customers directory, conversation detail, assistant test/live workspace, analytics and integration settings exist. Sandbox sessions must never contribute to production customer intelligence. Current assistant risk/delivery formulas are uncalibrated and must be removed.

Missing: durable customer event ledger, anonymous sessions/identity linking, website behavior tracking, WhatsApp adapter, courier/payment normalized evidence, scoring provenance/confidence, and durable recommendation workflow.

Implementation sequence: (1) tenant event ledger and projection service; (2) restricted public tracking and storefront instrumentation; (3) Messenger evidence; (4) WhatsApp signed ingress and outbound transport; (5) courier evidence normalization; (6) verified payment evidence; (7) trust scoring; (8) multi-signal intelligence; (9) dashboard timeline/intelligence; (10) persisted merchant actions; (11) full validation.

API plan: authenticated customer timeline/intelligence/actions; channel-scoped public tracking; provider-specific verified ingress. Never trust browser-submitted customer IDs, paid amounts, delivery outcomes or tenant IDs. Provider credentials must remain server-side. External provider live verification depends on provisioned accounts and credentials; document unverified provider capabilities rather than reporting simulated calls as live integrations.

Compatibility: retain all auth, tenancy, order/stock and AI flows. Extend central persistence points. Events use stable deduplication keys; repeat webhooks must not inflate scores. Anonymous tracking has retention and contains allowlisted metadata only. Identity association requires a server-validated interaction, never an arbitrary browser customer ID. Probabilities require observed outcomes; behavioral heuristics are identified as scores, not calibrated probabilities.

Git: the repository started with extensive uncommitted previous work. Commit only changes made for this roadmap; preserve existing work.

Validation strategy: phase-specific unit/API tests plus backend typecheck. Frontend phases additionally check frontend types. Final pass runs workspace typechecks, lint, tests and builds. Run browser/API checks without sending messages to real customers or charging payments.

## Final delivery report

Available merchant surfaces: `/intelligence` for actions and profile coverage; `/customers/:id` for customer history; intelligence alongside `/conversations/:id` and active conversations in `/assistant`; `/settings/intelligence` for provider configuration and read-only verification of existing payments/parcels. Empty accounts show empty states, not sample customer scores.

Implemented data path: website activity or channel message → tenant-scoped event ledger → customer association → order/payment/courier evidence → versioned customer intelligence → durable merchant actions. Existing authentication, inventory, order creation, AI processing and human takeover flows remain in use. Merchant billing is separate from customer payment evidence.

### Activation and operational boundaries

1. Configure provider credentials through the administrator settings. Values are encrypted server-side. Use a public HTTPS backend URL plus the callback paths shown after saving credentials. Messenger and Steadfast retain their existing connection settings.
2. WhatsApp requires `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, `META_GRAPH_API_VERSION`, the existing Meta credential encryption configuration, and a registered number/system-user token. Configure the `/whatsapp` callback in Meta. Text is supported; media and delivery-status projection remain follow-up work.
3. Run the existing agent worker (`npm run worker -w apps/agent`) with the existing database/Redis environment to process channel jobs and the five-minute intelligence sweep. Manual refresh is also available in Customer operations. Local validation did not launch a worker against the configured application database.
4. SSLCommerz matches `tran_id` to the SellPilot order number and validates amount/currency. Wallet receipts are supported through SSLCommerz; direct bKash/Nagad APIs are not enabled. Stripe PaymentIntent metadata must include `sellpilot_order_number`; Stripe supports pending, paid, failed and refunded evidence. These adapters ingest existing transactions and do not create charges. Currency matching currently supports BDT orders.
5. RedX requires the parcel's `merchant_invoice_id` to match the SellPilot order number. Link its tracking ID using Verify existing transaction or parcel. Pathao callbacks likewise require a matching `merchant_order_id`; Steadfast uses its existing synchronization flow.
6. Sandbox receipts never become verified production trust evidence. Provider-specific live acceptance tests remain pending provisioned accounts and credentials. SSLCommerz failed/refund reconciliation and direct wallet integration are not complete; this report does not represent them as shipped.

Purchase intent and customer value are explainable heuristic scores. Fake-customer probability stays unavailable without a calibrated model; the UI shows evidence-based risk indicators instead. Delivery success is an observed historical rate with sample size, not a predictive promise. Refunds alone do not establish fraud. Actions are merchant-facing recommendations/reminders and do not automatically message customers or enforce payment terms.

Validation limitations: browser inspection covered the current authenticated empty merchant account, not a populated production customer journey or every viewport size. The MongoDB journey uses controlled evidence rather than real external payments/courier deliveries. Lint/build retain four pre-existing dashboard image optimization warnings and a Browserslist freshness notice; there were no errors. All phases have implementation checkpoints, but the remaining provider and live-acceptance gaps above prevent a claim of complete production activation.
